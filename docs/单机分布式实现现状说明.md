# 单机分布式实现现状说明

## 一、文档目的

本文档用于说明当前 `FederatedScope / GGEUR` 在单机环境下的分布式实现现状。

这里的“单机分布式”指：

- server 和多个 client 都运行在同一台机器上
- 每个角色是独立 Python 进程
- 进程之间通过真实 gRPC 通信
- 不使用 standalone 内存直连模拟

因此，当前实现已经验证了真实分布式通信路径和 server/client 生命周期，但数据仍主要来自同一台机器上的共享数据目录，尚不等价于严格真实多机联邦学习。

## 二、当前实现的总体形态

当前单机分布式验证采用如下结构：

```text
同一台机器
├── server 进程
│   ├── 监听 server_port
│   ├── 等待 client join
│   ├── 聚合 GGEUR statistics
│   ├── 下发 global covariance / prototype
│   ├── 聚合模型参数
│   └── 发送 finish 并关闭 gRPC
│
├── client 1 进程
│   ├── 监听 client_port_1
│   ├── 连接 server
│   ├── 加载自己的数据分片
│   ├── 上传 local statistics
│   ├── 执行 GGEUR augmentation
│   └── 本地训练并上传模型参数
│
├── client 2 进程
├── client 3 进程
└── client 4 进程
```

当前已重点验证的样板是：

- `OfficeHome + GGEUR + FedAvg + CLIP ViT-B-16`
- 单机真实 gRPC server + 4 client 进程
- 4 个 client 对应 4 个 domain

同时还完成了 `OfficeHome` 和 `DomainNet` 下多种方法的短链路验证，包括 `FedAvg`、`FedProx`、`FedOpt`、`MOON`、`FedProto`、`PromptFL`。

## 三、通信规则

### 1. 启动顺序

当前默认启动顺序是：

1. 先启动 server
2. server 开始监听 `server_host:server_port`
3. 再启动各个 client
4. client 通过 `server_host:server_port` 连接 server
5. server 给每个 client 分配真实 client ID

在单机验证中，常见配置是：

```yaml
distribute:
  use: True
  role: server
  server_host: 127.0.0.1
  server_port: 51051
```

client 侧使用：

```yaml
distribute:
  use: True
  role: client
  server_host: 127.0.0.1
  server_port: 51051
  client_host: 127.0.0.1
  client_port: 51052
```

不同 client 使用不同 `client_port`，避免端口冲突。

### 2. client join 规则

server 启动后进入 join 阶段。

当前规则：

- server 等待配置中的 `client_num` 个 client 加入
- client 成功连接后，server 为其分配真实 client ID
- server 记录已加入 client
- 如果在 join timeout 内 client 没有全部加入，server 抛出超时错误并退出

该机制解决了过去 server 无限等待 client 的问题。

典型异常日志形式：

```text
Timeout waiting for clients to join. Expected 4 clients, but only 3 joined
TimeoutError: Only 3/4 clients joined after 60 seconds
```

### 3. client ID 分配前的消息处理

client 在拿到 `assign_client_id` 前，可能先收到其他 server 消息。

当前机制：

- client 在获得真实 client ID 前先缓存其他消息
- 收到 `assign_client_id` 后，再回放缓存消息
- 避免启动顺序、网络延迟或消息乱序导致 client 状态异常

该机制已经通过 `delayed_client` 场景验证。

### 4. GGEUR round 0 通信规则

GGEUR 分布式流程中，round 0 不是普通模型训练轮，而是统计与增强准备阶段。

通信流程：

1. client 加载本地数据分片
2. client 提取本地特征
3. client 计算 local mean / covariance / count
4. client 上传 local statistics 到 server
5. server 收齐所有 client 的 statistics
6. server 聚合 global covariance
7. server 构建 global prototypes 和 cross-client prototypes
8. server 下发全局统计信息给 client
9. client 接收后执行 GGEUR augmentation
10. client 完成增强后发送 `augmentation_ready`
11. server 收齐 ready 后进入后续训练轮

当前该链路已经在 `OfficeHome + GGEUR + FedAvg` 下完整通过。

### 5. 训练轮通信规则

进入 round 1 及后续 round 后，流程为同步联邦训练。

当前规则：

- server 向 client 下发当前全局模型参数
- client 使用本地数据进行训练
- client 上传本地模型更新
- server 等待本轮应参与 client 的模型更新
- server 收齐后执行聚合
- server 进入下一轮

当前是同步聚合：

```text
server 等待全部应参与 client 返回 -> 聚合 -> 下一轮
```

如果某个 client 在训练中崩溃或长时间不返回，server 依赖 GGEUR 阶段 watchdog 触发 timeout，不会无限等待。

### 6. finish 收尾规则

训练完成后：

1. server 发送 `finish` 消息给 client
2. client 收到 finish 后停止训练逻辑
3. client 调用通信 shutdown
4. server 调用通信 shutdown
5. gRPC server 停止
6. 进程退出并释放端口

当前已经修复过训练完成后 server 进程不退出的问题，`terminate()` 和 GGEUR `_finish()` 都做了幂等和通信关闭处理。

## 四、数据集持有方式

### 1. 当前单机数据持有方式

当前单机分布式验证中，数据通常是放在同一台机器上的共享数据目录中。

即：

```text
同一台机器
├── 数据根目录
│   ├── OfficeHome
│   ├── DomainNet
│   └── PACS
├── server 进程
├── client 1 进程
├── client 2 进程
├── client 3 进程
└── client 4 进程
```

每个 client 进程通过配置和数据加载逻辑选择自己的数据分片。

因此当前是：

```text
逻辑上：每个 client 只训练自己的数据分片
物理上：所有数据仍位于同一台机器的共享数据目录
```

这与真实多机联邦学习仍有差距。

真实联邦学习应为：

```text
server 机器：不持有 client 训练数据
client 1 机器：只持有 client 1 本地数据
client 2 机器：只持有 client 2 本地数据
client 3 机器：只持有 client 3 本地数据
client 4 机器：只持有 client 4 本地数据
```

### 2. OfficeHome 当前划分方式

OfficeHome 验证中，常用设置是 4 个 client 对应 4 个 domain。

典型 domain：

- `Art`
- `Clipart`
- `Product`
- `RealWorld`

单机验证时，各 client 从同一份 OfficeHome 数据根目录中读取自己对应 domain 的数据。

因此：

- client 1 逻辑上只训练 domain 1
- client 2 逻辑上只训练 domain 2
- client 3 逻辑上只训练 domain 3
- client 4 逻辑上只训练 domain 4

但这些 domain 数据物理上仍可能在同一个数据根目录下。

### 3. DomainNet 当前划分方式

DomainNet 验证中，当前主要使用 4 个 domain：

- `clipart`
- `painting`
- `real`
- `sketch`

每个 client 对应一个 domain 或一个数据分片。

DomainNet 类别数和统计量更大，因此在分布式通信中暴露了更明显的大 payload 问题。当前已经通过压缩 statistics / covariance / prototype payload 缓解。

### 4. server 是否持有数据

当前实现已经开始向真实 FL 边界收敛：

- 在 distributed 模式下，server 侧不应构建 client 训练数据
- client 侧根据自己的配置和 `data_idx` 加载对应训练数据

但从严格真实 FL 角度看，当前仍有差距：

- 单机验证中 server 和 client 仍在同一台机器
- 数据根目录通常仍在本机可见
- server-side evaluation 在部分流程中仍可能依赖集中测试数据

因此当前结论是：

```text
当前已经实现 client 逻辑分片训练，
但尚未完全实现物理数据隔离。
```

下一步多机验证需要改为预切分数据，并让每台 client 机器只持有自己的本地数据。

## 五、模型和权重持有方式

### 1. 当前单机模型持有方式

当前单机分布式中：

- server 进程持有全局模型状态
- client 进程各自持有本地模型副本
- 每轮训练时，server 下发全局模型参数
- client 在本地训练后上传更新
- server 聚合后更新全局模型

模型参数通过 gRPC 消息传输。

### 2. 预训练权重持有方式

对于 `CLIP ViT-B-16`、timm 模型、CNN backbone 等，当前单机验证中通常所有进程都可以访问同一台机器上的模型权重或缓存目录。

也就是说：

```text
物理上：server/client 进程共享同一台机器上的模型权重文件
逻辑上：每个 client 独立加载自己训练所需的模型组件
```

真实多机部署时，需要保证：

- 每台 client 机器都有对应模型权重
- 权重路径在配置中明确
- server 机器如果不做特征提取或评估，则不应依赖 client 的本地权重
- 不同机器的模型缓存目录不能混淆

### 3. GGEUR 特征提取器持有方式

GGEUR 中，client 需要使用特征提取器计算本地特征，例如 CLIP / ViT。

当前规则：

- client 本地加载 extractor
- client 本地提取 feature
- client 上传统计量，而不是上传原始图片
- server 聚合 statistics 和 prototypes

这已经符合“不上传原始数据”的基本联邦学习思路。

但在单机验证中，extractor 权重和数据仍位于同一台机器，因此还不是严格多机隔离。

## 六、GGEUR 分布式数据流

当前 GGEUR 分布式数据流可以概括为：

```text
client local data
    -> client feature extractor
    -> local features
    -> local mean / covariance / count
    -> server aggregation
    -> global covariance / global prototype / cross-client prototype
    -> client augmentation
    -> client local training
    -> model parameter upload
    -> server aggregation
```

重点是：

- 原始图像数据不上传到 server
- client 上传的是统计量和模型参数
- server 下发的是全局统计和模型参数
- GGEUR augmentation 在 client 侧执行

当前已验证的关键日志包括：

```text
Server: Broadcasted global covariances to 4 clients
Server: Client 4 augmentation ready (4/4)
Server: Round 1 aggregation complete
Server: Round 2 aggregation complete
Server: Round 3 aggregation complete
Server: Round 4 aggregation complete
Server: Training finished after 5 rounds
```

## 七、现有鲁棒机制

### 1. join timeout

server 等待 client 加入时有超时机制。

覆盖问题：

- client 没启动
- client 数量不够
- client 连错地址
- 网络不可达

验证场景：

- `missing_client_timeout`

效果：

- server 不再无限等待
- 日志会输出期望 client 数、已加入 client 数和已加入 ID

### 2. client ID 前消息缓冲

client 在收到真实 ID 前会缓存其他消息。

覆盖问题：

- client 启动顺序不一致
- server/client 消息到达顺序不稳定
- client 尚未初始化 ID 时收到训练相关消息

验证场景：

- `delayed_client`

效果：

- 延迟启动 client 仍可正常 join 并进入训练

### 3. GGEUR 分布式阶段 watchdog

当前新增了 GGEUR 专用阶段超时机制。

配置项：

```yaml
ggeur:
  distributed_stage_timeout: 1800
```

覆盖阶段：

- `statistics`
- `augmentation_ready`
- `round_N_model_updates`

覆盖问题：

- client join 后崩溃
- client 在 statistics 阶段不上传
- client 在 augmentation 阶段不 ready
- client 在训练轮中崩溃或不上传模型参数

验证场景：

- `client_crash_after_join`
- `client_crash_during_round`

效果：

- server 到时主动失败
- 输出明确阶段日志
- 通知已 join client finish
- 关闭 gRPC server

### 4. 端口冲突检测

验证脚本中覆盖了 server 端口被占用的场景。

验证场景：

- `port_conflict`

效果：

- server 启动失败时输出明确错误
- 不会静默进入等待阶段

典型日志：

```text
RuntimeError: Failed to bind to address 127.0.0.1:51051
```

### 5. client 错误 server 端口验证

验证脚本覆盖了 client 连接错误 server 端口的场景。

验证场景：

- `client_wrong_server_port`

典型日志：

```text
StatusCode.UNAVAILABLE
failed to connect to all addresses
Connection refused
```

效果：

- client 连接错误可被明确识别
- 不会误判为训练逻辑问题

### 6. 重复启动停止验证

验证脚本覆盖了连续启动/停止 server 的场景。

验证场景：

- `repeat_start_stop`

效果：

- PID 文件能被清理
- 端口能释放
- 下一次启动不受上一次残留进程影响

### 7. gRPC 大 payload 处理

GGEUR 会传输较大的 statistics、covariance 和 prototype。

当前已经处理的问题：

- OfficeHome 中 covariance 直接作为嵌套 list 下发会导致 broadcast 阻塞
- DomainNet 中 local statistics 可能超过 gRPC 消息上限

现有机制：

- ndarray / tensor 叶子节点编码为紧凑 payload
- DomainNet statistics 使用 `numpy + zlib + base64` 压缩
- float16 传输表示，server 解码后转回 float32
- client 统一反序列化为 ndarray

效果：

- OfficeHome 的 global covariance 下发已通过
- DomainNet 的方法短链路验证已通过

### 8. 模型参数反序列化兼容

分布式 gRPC 传输后，模型参数 payload 类型可能发生变化。

已修复问题：

- `(sample_size, model_para)` 从 tuple 变成 list
- tensor 参数经过 base64/pickle 序列化后需要还原

当前机制：

- server 聚合前兼容 list/tuple 形式
- 聚合前使用参数反序列化逻辑恢复 tensor
- 非法或空模型参数会被识别

效果：

- 不再出现 `No valid model parameters received`
- FedAvg 聚合可正常完成

### 9. 训练结束通信关闭

已修复训练完成后 server 进程不退出的问题。

当前机制：

- `gRPCCommManager` 提供 `shutdown()`
- server `terminate()` 幂等
- GGEUR `_finish()` 显式 shutdown
- client 收到 finish 后 shutdown
- 空 finish content 不再被误处理为模型参数

效果：

- 训练结束后 gRPC server 可释放
- 进程可正常退出
- 后续实验可复用端口

## 九、当前实现与真实联邦场景的差距

### 1. 物理数据隔离尚未完成

当前是共享数据目录上的逻辑分片。

真实联邦场景要求：

- 每个 client 物理持有自己的数据
- server 不持有 client 训练数据
- client 之间不能互相访问数据

### 2. 跨主机网络尚未验证

当前通信发生在同一台机器。

真实多机还需要验证：

- server 真实 IP 监听
- client 跨机器连接
- 防火墙和端口映射
- 网络延迟和断链
- 多机日志收集

### 3. client-side evaluation 尚未完全固化

严格 FL 中，server 不应直接读取所有 client 的测试数据。

后续应推进：

- client 本地评估
- client 上传 metrics
- server 只做指标汇总

### 4. 动态新用户加入尚未支持

当前 `client_num` 基本在实验开始前固定。

训练中途加入新用户目前不作为已实现能力。

建议近期策略：

- join 窗口结束后拒绝新 client 参与本次训练
- 新用户进入 pending 列表
- 下一次实验或下一轮安全边界再考虑加入

### 5. 异步联邦训练尚未支持

当前是同步聚合。

即：

```text
server 等待本轮应参与 client 返回后再聚合
```

后续如需处理慢 client，可以先做 quorum 聚合，再考虑完全异步 FL。

## 十、当前结论

当前单机分布式实现已经完成了真实 gRPC 通信、GGEUR 统计与增强、模型参数聚合、异常超时和进程收尾的关键验证。

它可以被定义为：

```text
单机真实通信的联邦学习分布式验证环境
```

但还不能定义为：

```text
严格真实多机联邦学习部署
```

下一步应优先推进：

1. 两机最小通信验证
2. 两机多 client 的 `OfficeHome + GGEUR + FedAvg` 样板
3. client 物理数据隔离
4. client-side evaluation
5. 多机启动、停止、状态检查和日志收集脚本
