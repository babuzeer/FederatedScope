### 延迟启动 client 验证

- 验证目标：
  - 验证客户端在 `assign_client_id` 前的消息缓冲机制是否有效
- 执行方式：
  - 手动先启动 server
  - 延迟启动 client 1
  - 再间隔启动 client 2、client 3
- 验证结果：
  - 所有 client 都成功拿到 ID
  - server 最终正常进入训练并完成输出
  - 整个过程中没有异常 traceback
- 当前结论：
  - `assign_client_id` 前消息缓冲机制工作正常
  - client 启动顺序存在延迟时，distributed 训练仍可稳定进入训练流程

### 缺少一个 client 的超时验证

- 当前测试超时时间：
  - `60` 秒
- 初始现象：
  - server 一直卡在等待阶段
  - 没有开始训练，也没有自动退出
- 根因定位：
  - join 阶段阻塞在 `comm_manager.receive()`
  - 底层 `gRPC receive()` 是无限等待
  - 没有新消息到达时，join timeout 检查不会执行
- 修复内容：
  - [gRPC_server.py](/D:/Projects/FederatedScope/federatedscope/core/gRPC_server.py)
  - [communication.py](/D:/Projects/FederatedScope/federatedscope/core/communication.py)
  - [server.py](/D:/Projects/FederatedScope/federatedscope/core/workers/server.py)
- 验证方式：
  - 启动 server
  - 只启动 `client_1`、`client_2`
  - 故意不启动 `client_3`
- 验证结果：
  - server 在约 `60.3` 秒后按预期退出
  - 日志输出：
    - `Timeout waiting for clients to join. Expected 3 clients, but only 2 joined after 60.3 seconds. Joined client IDs: [1, 2]`
  - 异常输出：
    - `TimeoutError: Only 2/3 clients joined after 60 seconds`
- 当前结论：
  - server join timeout 已按预期生效
  - 缺少 client 的场景下不会再无限卡死
