# 分布式实施记录日志

本文档用于持续记录 `FederatedScope / GGEUR` 分布式部署推进过程中的实际操作、验证结果、问题现象与下一步计划。

## 2026-05-25 已实现并验证的分布式机制汇总

本节汇总当前已经落地并通过验证的分布式系统机制。当前结论仅覆盖单机可模拟的真实分布式流程；两机或多机跨主机网络验证仍需后续在具备多台机器时执行。

### 一、基础分布式通信与生命周期机制

- 已实现机制：
  - server / client 基于 gRPC 的分布式启动与连接。
  - client join 后由 server 分配真实 client ID。
  - server 端 join 阶段支持超时退出，避免缺少 client 时无限等待。
  - client 端可处理 server 结束时的 finish 消息。
  - server/client 退出后可清理进程并释放端口。

- 已验证场景：
  - `normal`：4 个 client 正常 join、训练、聚合、finish。
  - `delayed_client`：client 延迟启动仍可正常 join 并进入训练。
  - `missing_client_timeout`：缺少 client 时 server 按预期触发 join timeout。
  - `repeat_start_stop`：server 连续启动/停止两轮后无残留进程，端口可复用。

### 二、GGEUR 分布式统计、增强与聚合链路

- 已实现机制：
  - client 在 round 0 提取本地特征并上传 local statistics。
  - server 聚合各 client 的 local mean / covariance / count。
  - server 生成并下发 global covariance、cross-client prototypes、global prototypes。
  - client 收到全局统计后执行 GGEUR augmentation。
  - client 完成增强后向 server 回报 `augmentation_ready`。
  - server 在所有 client ready 后启动 round 1+ 的模型训练。
  - server 可聚合 client 返回的模型参数，支持 list/tuple 形式的模型参数 payload。

- 已验证场景：
  - `normal`：`OfficeHome + GGEUR + FedAvg + CLIP ViT-B-16` 单机真实分布式完整链路通过。
  - 关键日志已经出现：
    - `Round 1/2/3/4 aggregation complete`
    - `Training finished after 5 rounds`
  - 已确认不再出现阻塞性错误：
    - `No valid model parameters received`

### 三、分布式 payload 序列化与反序列化机制

- 已实现机制：
  - server 下发 covariance / prototype 时将 ndarray / tensor 编码为紧凑字符串 payload。
  - client 收到后通过统一反序列化路径恢复为 ndarray。
  - client 对 covariance、prototype、feature 维度进行校验，避免 stale cache 或维度不一致导致后续训练隐性失败。
  - server 对 client 上传的 statistics 进行 shape 校验，发现错误时提前失败并给出明确日志。

- 已验证场景：
  - `normal`：完成 global covariance / prototype 下发、client 解码、augmentation、训练和 FedAvg 聚合。
  - `system_short` 中的异常路径验证未发现 payload 解码导致的额外失败。

### 四、GGEUR 分布式阶段 watchdog 机制

- 已实现机制：
  - 新增 `ggeur.distributed_stage_timeout` 配置项，默认 `1800` 秒。
  - 设置 `<= 0` 可关闭 watchdog。
  - server 端记录并监控以下 GGEUR 分布式阶段：
    - `statistics`
    - `augmentation_ready`
    - `round_N_model_updates`
  - 阶段超时后 server 输出明确错误日志，通知已 join client finish，并 shutdown gRPC server。

- 已验证场景：
  - `client_crash_after_join`：
    - client join 后立即崩溃。
    - server 在 `statistics` 阶段 20 秒后超时退出。
  - `client_crash_during_round`：
    - client 已完成 round 0 并进入 round 1 训练。
    - 训练轮中 kill client。
    - server 在 `round_1_model_updates` 阶段 20 秒后超时退出。

  - `scripts/distributed_scripts/ggeur_domainnet_vit/run_method_validation.sh`
- 验证策略：
  - 使用短链路子集验证，避免完整 DomainNet 长实验阻塞方法链路确认。
  - 保留 GGEUR 生成数据路径。
  - PromptFL 使用 `prompt_max_train_batches=1` 验证 prompt forward/backward、参数上传和聚合。

### 本轮暴露并修复的问题

1. DomainNet local statistics 超过 gRPC 消息上限
   - 现象：
     - client 上传 local statistics 时出现：
       - `Received message larger than max (706747638 vs. 314572800)`
   - 原因：
     - DomainNet 类数远多于 OfficeHome，单个 client 上传数百个 `512 x 512` covariance matrix，原始 payload 过大。
   - 修复：
     - client 上传 local statistics 时对 ndarray/tensor payload 做 `numpy + zlib + base64` 压缩。
     - payload 传输时使用 float16 压缩表示，server 解码后转回 float32 使用。
     - server 下发 global covariance/prototype 时也走同一压缩格式。

2. DomainNet PromptFL GPU 并发 OOM
   - 现象：
     - 4 个 client 并行训练 PromptFL 文本编码器时 GPU 显存不足。
   - 处理：
     - DomainNet PromptFL 验证改为 CPU 路径。
     - 用 `prompt_max_train_batches=1` 做短链路方法验证。

3. DomainNet PromptFL server 侧全量 test evaluation 过重
   - 现象：
     - PromptFL 已完成 client 训练和上传后，server 加载接近全量 DomainNet test split 做评估，验证耗时过长。
   - 修复：
     - server 支持 `eval.freq <= 0` 时跳过 server-side MLP/Prompt/CNN test evaluation。
     - DomainNet PromptFL 验证配置中设置 `eval.freq=0`，聚合完成后直接 finish。

- 修复内容：
  - [gRPC_server.py](/D:/Projects/FederatedScope/federatedscope/core/gRPC_server.py)

  - server 在约 `60.3` 秒后按预期退出

    - `Timeout waiting for clients to join. Expected 3 clients, but only 2 joined after 60.3 seconds. Joined client IDs: [1, 2]`

    - `TimeoutError: Only 2/3 clients joined after 60 seconds`

## 2026-05-21

### 训练完成后 server 进程不退出问题

- 问题现象：
  - 所有训练轮次已经完成
  - server 已经输出训练结束日志
  - 但 server 进程没有自动退出

- 根因定位：
  - 分布式模式下 `gRPCCommManager` 会启动本地 gRPC server 和线程池
  - 原有训练结束路径只发送 `finish` 消息，没有显式关闭 gRPC server
  - GGEUR 自定义 `_finish()` 会在回调中结束训练，而基类 `Server.run()` 退出循环后仍可能再次调用 `terminate()`
  - 因此存在“训练逻辑结束，但通信线程仍存活”以及重复收尾的风险

- 修复内容：
  - `federatedscope/core/communication.py`
    - 为 `StandaloneCommManager` / `StandaloneDDPCommManager` / `gRPCCommManager` 增加统一 `shutdown()` 接口
    - `gRPCCommManager.shutdown()` 中调用 `grpc_server.stop()` 并等待关闭
  - `federatedscope/core/workers/server.py`
    - `Server.run()` 在最终收尾前检查 `is_finish`
    - `terminate()` 改为幂等，避免重复发送 finish 或重复关闭通信
    - `terminate()` 发送 finish 后显式调用 `comm_manager.shutdown()`
  - `federatedscope/core/workers/client.py`
    - client 收到 `finish` 后调用 `comm_manager.shutdown()`
    - 对空 `finish` content 做保护，避免把 `{}` 当作模型参数更新 trainer
  - `federatedscope/contrib/worker/ggeur_server.py`
    - GGEUR `_finish()` 中发送 finish 后关闭通信
    - 将 `state` 推进到 `total_round_num + 1`，确保基类运行循环能退出
    - `finish` 消息使用空 dict 作为 content，兼容消息序列化

- 验证结果：
  - 已执行语法检查：
    - `python -m py_compile federatedscope\core\communication.py federatedscope\core\workers\server.py federatedscope\core\workers\client.py federatedscope\contrib\worker\ggeur_server.py`
  - 结果通过

- 当前结论：
  - server 在训练完成后应能正常释放 gRPC 通信资源并退出进程
  - 该修复同时覆盖普通 `Server.terminate()` 路径和 GGEUR 自定义 `_finish()` 路径
