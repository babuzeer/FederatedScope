## 二、QPS 的含义与当前统计

"QPS（Queries Per Second）"在本项目中有多种合理解释，不同解释对应不同的优化目标。以下逐一分析当前数值。

### 解释 1：数据增强吞吐量（最相关）

**定义**：每秒生成的增强特征样本数量，反映高斯采样阶段的处理速度。

**当前统计**（来自本次日志）：
- 单客户端：3250 个样本 / 65s ≈ **50 samples/s**
- 60 个客户端串行总量：195,000 个样本 / 3993s ≈ **49 samples/s**（串行无并发收益）

| 指标 | 数值 |
|------|------|
| 单客户端增强耗时 | ~65s |
| 单客户端生成样本数 | 3,250（65 类 × 50/类） |
| 当前增强 QPS | **~50 samples/s** |
| 目标 QPS | 10,000 samples/s |
| 差距 | **200×** |

---

### 解释 2：CLIP 特征提取吞吐量

**定义**：每秒通过 CLIP ViT-B-16 编码的原始图片数量。

**当前统计**（本次日志全部命中缓存，无法直接读取）：
- 本次日志：2623 张图片全部命中缓存，提取耗时 ~2s，**无有效 QPS 数据**
- 理论估算（ViT-B-16，单 GPU，batch_size=32）：**200–500 img/s**

| 指标 | 数值 |
|------|------|
| 原始训练样本总数 | 2,623（LDS 后） |
| 本次缓存命中率 | 100% |
| 当前提取 QPS | 无法统计（缓存命中） |
| 理论 QPS（无缓存） | ~200–500 img/s |
| 目标 QPS | 10,000 img/s |
| 差距 | 20–50× |

> QPS 计时代码已加入 `ggeur_client._extract_features()`，清空缓存后重跑可获得真实数值。

### 解释 3：联邦通信吞吐量

## 三、实现 10,000+ QPS 的方案

### 方案 1：多进程并行增强（推荐，改动最小）

**目标**：将 60 个客户端的增强从串行改为并行。

当前串行耗时 = 60 × 65s = 3900s。若 60 个客户端并行，理论耗时降至 65s。

```python
from multiprocessing import Pool

def augment_client(client_id):
    # 每个进程独立执行增强
    ...

with Pool(processes=min(60, cpu_count())) as pool:
    pool.map(augment_client, range(1, 61))
```

**预期收益**：增强阶段从 66 分钟降至 1–2 分钟，整体训练时间从 74 分钟降至 ~10 分钟。

---

### 方案 2：GPU 批量化高斯采样

**目标**：将增强中的高斯采样从 CPU numpy 迁移到 GPU torch，利用 GPU 并行计算。

当前瓶颈在于每个类逐一采样（65 类 × 50 samples），可改为一次性批量生成：

```python
# 当前（CPU，逐类）
for class_idx in range(num_classes):
    samples = np.random.multivariate_normal(mean, cov, n)

# 优化后（GPU，批量）
means = torch.stack([class_means[c] for c in classes]).cuda()   # (C, D)
# 使用 torch.distributions.MultivariateNormal 批量采样
dist = torch.distributions.MultivariateNormal(means, covariance_matrix=covs)
samples = dist.sample((n_per_class,))  # (n, C, D)
```

**预期收益**：单客户端增强时间从 65s 降至 1–5s，QPS 提升 10–50×。

---

### 方案 3：预计算并缓存增强数据

**目标**：增强只在第一轮执行一次，后续轮次直接复用，避免重复计算。

当前每次训练都重新生成增强数据。由于增强是基于统计量（均值/协方差）的确定性过程，可以将生成的增强特征持久化到磁盘：

```python
aug_cache_path = f"aug_cache/client_{client_id}_round0.npz"
if os.path.exists(aug_cache_path):
    data = np.load(aug_cache_path)
else:
    data = _run_augmentation(...)
    np.savez(aug_cache_path, features=data['features'], labels=data['labels'])
```

**预期收益**：第二次及后续实验的增强阶段耗时接近 0，适合超参数调优场景。

---

### 方案 4：减少增强样本数量（快速验证用）

**目标**：在不改代码结构的前提下，通过配置降低增强量，快速验证实验。

当前配置：
```yaml
num_generated_per_sample: 50
num_generated_per_prototype: 50
target_size_per_class: 50
```

调整为：
```yaml
num_generated_per_sample: 10
num_generated_per_prototype: 10
target_size_per_class: 10
```

**预期收益**：增强时间线性缩短约 5×，适合调试阶段使用，精度可能略有下降。

---

### 方案 5：分布式特征提取（多 GPU / 多机）

**目标**：若服务器有多张 GPU，将 60 个客户端分配到不同 GPU 并行执行特征提取和增强。

```python
# 按 GPU 数量分组客户端
gpu_count = torch.cuda.device_count()
client_groups = [list(range(i, 60, gpu_count)) for i in range(gpu_count)]

# 每个 GPU 启动一个进程处理对应客户端组
for gpu_id, clients in enumerate(client_groups):
    Process(target=run_clients, args=(clients, gpu_id)).start()
```

**预期收益**：若有 4 张 GPU，增强阶段理论加速 4×，CLIP 提取加速 4×，综合 QPS 可达 200–2000 samples/s。

---

## 四、方案对比

| 方案 | 实现难度 | 预期 QPS 提升 | 是否需要重构 |
|------|----------|---------------|--------------|
| 多进程并行增强 | 低 | 20–60× | 否 |
| GPU 批量高斯采样 | 中 | 10–50× | 部分 |
| 增强结果缓存 | 低 | 首次无收益，后续接近 ∞ | 否 |
| 减少增强样本数 | 极低 | 5× | 否（改配置） |
| 多 GPU 分布式 | 高 | 4–8×（取决于 GPU 数） | 是 |

**建议优先级**：方案 1（多进程并行）+ 方案 2（GPU 批量采样）组合，可在改动较小的情况下将增强 QPS 从 50 提升至 1000–5000 samples/s，配合多 GPU 有望达到 10,000+ QPS。
