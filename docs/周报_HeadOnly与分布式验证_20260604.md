# 周报：HeadOnly 方案与分布式验证进展

时间：2026-06-04

## 1. 本周目标

本周围绕 GGEUR HeadOnly 方案和后续多机分布式验证，主要推进以下目标：

1. 将 HeadOnly 从简化 QPS 原型改为完整系统方案。
2. 使用真实 OfficeHome 数据集和 ViT-B-16 特征，不再保留模拟数据/模拟特征。
3. 完成真实数据生成、增强样本缓存和 cache-hot 复跑逻辑。
4. 在单服务器上完成 60 客户端、100 轮 HeadOnly 训练验证。
5. 补充 QPS、通信量、准确率等系统指标日志。
6. 梳理多机分布式验证方案和 MLP 参数上传 1 万 QPS 的理论设备需求。

## 2. HeadOnly 完整方案实现

本周将 HeadOnly 方案从旧的离线/简化脚本推进为 FederatedScope/GGEUR 主流程中的完整系统路径。

已完成的核心逻辑包括：

1. 保留 round0 的完整 GGEUR 流程：
   ```text
   真实数据划分 -> ViT/CLIP 特征提取 -> 客户端统计量/协方差/原型上传
   -> 服务器聚合全局协方差/原型 -> 下发客户端 -> 生成增强样本
   ```

2. round0 后进入 HeadOnly 训练：
   ```text
   后续轮次只训练和通信 MLP head 参数
   ```

3. 增加 HeadOnly 配置项：
   ```text
   ggeur.head_only_mode
   ggeur.head_only_after_round0
   ggeur.headonly_cache_version
   ggeur.headonly_eval_mode
   ggeur.headonly_skip_round0_if_augmented_cache_exists
   ```

4. 增强客户端缓存逻辑：
   - 第一次完整运行时，生成增强样本并保存缓存。
   - 后续 cache-hot 运行时，如果增强样本缓存存在，可以跳过 round0 特征提取、统计上传和增强生成，直接加载缓存进入 MLP 训练。

5. 增加日志：
   - 本地统计量 payload bytes。
   - 增强样本生成时间和增强 QPS。
   - 每轮训练样本数、训练耗时、训练样本 QPS。
   - 训练结束通信量。
   - 最终准确率和 best 准确率。

主要修改文件：


## 5. 分布式验证代码实现

本周补充了分布式验证相关脚本和实验框架。

已实现内容：

1. 增加 HeadOnly 系统级配置和 runner。
2. 增加分布式短实验脚本：
   ```text
   scripts/distributed_scripts/ggeur_headonly_system_officehome_vit/run_distributed_short.sh
   ```

3. 支持动态生成 server/client 配置。
4. 支持按时间子目录保存实验日志。
5. 支持分布式阶段 timeout，用于避免客户端卡死后服务端无限等待。

本周尝试过单 GPU 上的短分布式实验。结果发现：

```text
多个分布式 client 同时加载 ViT/CLIP 做 round0 特征流程时，会在单 GPU/单机上产生严重竞争。
```

该问题说明后续多机分布式实验需要调整策略：

1. 先完成 raw feature cache 和 augmented feature cache。
2. 分布式训练阶段尽量使用 cache-hot。
3. 如果必须完整验证 round0，多客户端 ViT 特征提取应做错峰或放到多 GPU/多机器上。

因此当前分布式代码已具备基础验证框架，但正式多机验证还需要进一步实现：

```text
client -> subserver -> center server
```

的分层聚合和集中上传 QPS 统计。

## 6. MLP 参数上传 QPS 理论验证

本周重新明确了 1 万 QPS 的指标口径：

```text
不是整轮训练 QPS
不是训练样本 QPS
而是同步上传窗口内的 MLP 参数 upload request QPS
```

当前 HeadOnly MLP 参数大小：

```text
input_dim = 512
num_classes = 65
params = 512 * 65 + 65 = 33,345
float32 payload = 33,345 * 4 = 133,380 bytes ≈ 130 KiB
```

1 万 upload QPS 原始带宽需求：

```text
10,000 * 133,380 bytes/s = 1.33 GB/s
1.33 GB/s * 8 = 10.67 Gbps
```

考虑协议、序列化、TCP/gRPC 和调度开销，建议按：

```text
14-16 Gbps
```

设计。

当前服务器网卡显示：

```text
eth0_speed_Mbps = 10000
```

即当前服务器为 10GbE，单台作为上传入口时理论上不适合严格证明 1 万 upload QPS。

本周新增理论验证文档：

```text
docs/HeadOnly_MLP上传QPS理论验证与设备需求.md
```

结论：

```text
两台 10GbE：可做下界测试，不能严格证明 1 万+
四到五台 10GbE：可较可信模拟 1 万+
两台 25GbE：可更干净验证 1 万+
```

资金有限时推荐：

```text
2 台 10GbE 子服务器
2-3 台 10GbE 客户端压测机
中心服务器可与其中一台子服务器复用
```

更干净的验证方案：

```text
1 台 25GbE 子服务器 + 2 台 10GbE 客户端压测机
或 2 台 25GbE 服务器
```


该脚本目前只作为第一阶段理论估计工具。它与最终真实系统仍有差异：

```text
未走 FederatedScope/gRPC 消息栈
未做真实 state_dict 序列化
未经过真实多机网络
未做子服务器 FedAvg 聚合
未接入训练与准确率评估
```

后续需要逐步替换为真实协议路径。

## 8. 当前问题

1. 单机多客户端完整 round0 会受 ViT/CLIP 加载和 GPU 竞争影响，分布式完整 round0 需要错峰或多机多 GPU。
2. 当前正式训练仍是单服务器 standalone，尚未完成真正多机分层联邦训练。
3. 1 万 upload QPS 尚未在真实多机网络上验证，目前完成了理论计算和本机轻量压测。
4. 当前服务器为 10GbE，单台机器无法严格证明 1 万 upload QPS。
5. 远端仓库 git HEAD 状态异常，runner 中 `git rev-parse HEAD` 会输出 warning，但不影响实验运行。
