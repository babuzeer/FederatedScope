# 多机真实场景验证规划

## 一、目标与边界

本文档用于规划 `FederatedScope / GGEUR` 从“单机多进程真实 gRPC 分布式验证”推进到“多机真实网络部署验证”的实施路线。

当前已经完成的基础是：

- 单机真实 gRPC server/client 进程验证
- `OfficeHome + GGEUR + FedAvg` 完整链路验证
- `OfficeHome / DomainNet` 方法矩阵短链路验证
- 单机可模拟异常场景验证，包括端口冲突、client 缺失、client 崩溃、重复启停等

下一阶段多机验证的目标不是直接跑完整实验矩阵，而是确认真实网络、真实机器边界、真实数据隔离和真实运维流程能稳定工作。

## 二、多机真实场景需要覆盖的核心需求

### 1. 网络通信需求

多机验证首先要证明 server 与 client 可以通过真实网络稳定通信。

需要覆盖：

- server 监听真实网卡地址，而不是只监听 `127.0.0.1`
- client 可通过 server 的真实 IP 和端口连接
- 如果通信模式需要 server 回连 client，则 client 也必须暴露真实可达 IP 和端口
- server/client 端口无冲突
- 防火墙、安全组、云平台端口映射规则正确
- gRPC 大消息传输可用，尤其是 GGEUR statistics、covariance、prototype、model parameters
- 长时间训练过程中连接不会被空闲超时或代理规则中断

最低验收标准：

- server 能收到所有 client 的 join
- client 能收到 server 分配的 client ID
- 至少完成 round 0 的 statistics 上传与 server 聚合
- 至少完成 1 个模型训练 round 的参数上传与聚合

### 2. 角色隔离需求

多机验证必须从“模拟分布式”向“真实联邦学习部署”收敛。

需要覆盖：

- server 不持有 client 训练数据
- 每个 client 只访问自己的本地数据目录
- server/client 使用不同配置文件
- server/client 使用各自本地输出目录
- server 只做调度、统计聚合、模型聚合和指标汇总
- client 负责本地训练、本地评估和必要的本地特征统计

建议约束：

- 多机正式样板中不再依赖 server 运行时切分全部数据
- 每个 client 使用预切分后的本地数据目录
- server-side evaluation 默认关闭或仅做不涉及 client 原始数据的汇总

### 3. 数据与模型路径需求

真实多机环境下，路径问题往往比代码问题更容易造成失败。

需要覆盖：

- 每台机器上的数据路径明确
- 每个 client 的数据目录只包含自己的训练数据
- 测试数据采用 client-side evaluation 或预定义的本地测试划分
- CLIP / ViT / timm / CNN 等模型权重路径在各机器上可用
- 特征缓存目录与输出目录按机器隔离
- 日志目录和实验结果目录可回收、可归档

最低验收标准：

- 每个 client 启动时能打印自己实际使用的数据路径和样本数量
- server 启动时不加载 client 训练数据
- 所有机器的模型权重加载路径一致或有明确映射

### 4. 训练流程需求

多机验证至少需要覆盖一个完整同步 FL 训练闭环。

需要覆盖：

- server 启动并等待 client join
- client 完成本地数据加载
- GGEUR round 0 statistics 上传
- server 聚合 global covariance / prototype
- server 下发全局统计
- client 执行 augmentation
- client 本地训练
- server 聚合模型参数
- server 发送 finish
- client 正常退出
- server 正常释放 gRPC 资源

推荐第一样板：

- 数据集：`OfficeHome`
- 方法：`GGEUR + FedAvg`
- 特征提取器：`CLIP ViT-B-16`
- 拓扑：1 台 server + 1 台 client 机器承载 4 个 client 进程

该拓扑已经能验证跨主机网络，同时比“一台机器一个 client”更容易控制变量。

### 5. 异常与恢复需求

多机环境下必须覆盖真实故障，而不是只跑正常路径。

需要覆盖：

- client 启动失败
- client 延迟加入
- client 连接错 server 地址或端口
- server 端口被占用
- client 在 statistics 阶段崩溃
- client 在训练 round 中崩溃
- 某台机器训练中断
- server 训练完成后进程释放
- 中断后再次启动不受残留进程和端口影响

最低验收标准：

- 失败有明确日志
- server 不无限等待
- 已加入 client 能收到 finish 或自行超时退出
- 端口和进程可清理
- 下一次实验可以重新启动

### 6. 运维与可复现需求

多机验证不是一次性手工操作，应逐步固化为可复现流程。

需要覆盖：

- 机器清单
- SSH 别名
- server/client 角色分配
- GPU 分配
- 端口规划
- 配置文件命名规范
- 启动脚本
- 停止脚本
- 状态检查脚本
- 日志拉取和归档脚本
- 验证结果记录模板

最低验收标准：

- 不依赖手工记忆启动顺序
- 每次验证能找到完整日志
- 失败后能定位是哪台机器、哪个角色、哪个阶段失败

## 四、实施路线

### 阶段 0：多机环境盘点

目标：

- 明确有哪些机器可以参与验证
- 明确网络、GPU、数据、模型权重和 Python 环境是否一致

需要产出：

- 机器清单
- 每台机器的 SSH 别名
- 每台机器的内网/公网可达 IP
- 每台机器可用 GPU 编号
- 数据路径
- 模型权重路径
- Python/conda 环境路径
- 可开放端口范围

验收标准：

- server 机器和 client 机器之间可以互相 `ping` 或通过端口测试验证可达
- client 机器可以连接 server 监听端口
- Python 环境和依赖版本可运行现有 `federatedscope/main.py`

### 阶段 1：两机最小通信验证

拓扑：

- 机器 A：server
- 机器 B：1 个 client

目标：

- 先验证跨主机 gRPC 通信，不引入完整 GGEUR 复杂链路

建议任务：

- 使用最小 toy / LR 或极短配置
- 只要求 join、ID 分配、1 个简单 round

验收标准：

- server 日志出现 client join
- client 日志出现 assigned client ID
- server/client 正常 finish
- 两台机器无残留进程

### 阶段 2：两机多 client 验证

拓扑：

- 机器 A：server
- 机器 B：4 个 client 进程

目标：

- 复现当前单机多进程能力，但通信跨真实机器

建议任务：

- `OfficeHome + GGEUR + FedAvg + CLIP ViT-B-16`
- 先跑 1 个训练 round
- 通过后跑完整 5 round

验收标准：

- 4 个 client 全部 join
- server 收齐 local statistics
- server 下发 global covariance/prototype
- 4 个 client 完成 augmentation
- 至少完成 1 轮模型参数聚合
- 完整验证中出现 `Training finished`

### 阶段 3：真实数据隔离验证

拓扑：

- server 机器不放 client 训练数据
- client 机器只放自己的预切分数据

目标：

- 从“跨机器运行”推进到“符合真实联邦学习边界”

需要做：

- 定义 client 数据目录格式
- 生成或整理预切分数据
- 修改/确认 client 配置只指向本地数据
- server 关闭训练数据加载
- evaluation 改为 client-side 或汇总式指标

验收标准：

- server 无法访问 client 训练数据时仍可启动和完成训练
- 每个 client 日志显示只加载自己的数据
- 指标由 client 上报，server 只汇总

### 阶段 4：多机多 client 分散部署

拓扑：

- 机器 A：server
- 机器 B/C/D/...：client 分散部署

目标：

- 验证 client 分散在多台机器时的真实拓扑

需要覆盖：

- 每台 client 机器独立端口
- 每台 client 机器独立数据目录
- 每台 client 机器独立 GPU
- server 统一聚合来自不同机器的消息
- 单台 client 机器失败时 server 能明确报错

验收标准：

- 所有 client 跨机器 join
- 训练能完成至少 1 个 round
- 任意 client 机器断开时 server 能触发阶段超时

### 阶段 5：方法矩阵扩展

目标：

- 在真实多机拓扑下验证不同方法分支

建议顺序：

1. `FedAvg`
2. `FedProx`
3. `FedOpt`
4. `FedProto`
5. `MOON`
6. `PromptFL`

推进原则：

- 每次只扩一个方法
- 先短链路，后完整 round
- 先 OfficeHome，后 PACS，最后 DomainNet
- 每个方法保留独立日志目录和结果记录

### 阶段 6：长实验与结果汇总

目标：

- 从系统验证进入实验验证

需要覆盖：

- 完整训练轮数
- 结果指标
- 训练耗时
- 单轮通信耗时
- payload 大小
- GPU 显存
- client 训练时间分布
- 异常重试记录

输出：

- 多机实验结果表
- 失败案例表
- 方法对比结果
- 后续优化建议

## 五、训练中新用户加入的处理方案

训练过程中加入新用户是动态联邦学习问题。当前项目更接近固定 client 集合的同步 FL，因此不建议在第一阶段直接支持任意动态加入。应先明确策略，再实现。

### 方案 A：严格固定 client 集合

含义：

- 每次实验开始前固定 `client_num`
- join 阶段结束后不接受新 client 参与本次训练
- 训练中的新用户只能进入等待队列，下一次任务或下一轮实验再加入

优点：

- 实现简单
- 结果可复现
- 与当前同步 FL 框架最一致
- 不影响已有 GGEUR statistics、augmentation 和聚合逻辑

缺点：

- 不支持在线扩容
- 新用户无法立即贡献数据

建议：

- 第一阶段采用该方案
- 作为当前多机验证的默认策略

需要实现/确认：

- server 在 join 窗口关闭后拒绝或忽略新 client
- 新 client 收到明确消息，例如 `join_rejected_experiment_started`
- 日志记录新 client 尝试加入的时间和地址

### 方案 B：下一轮训练周期加入

含义：

- 新 client 可以在训练过程中注册
- 但不参与当前 round
- server 在安全边界处，例如下一轮开始前，决定是否纳入

难点：

- `client_num` 和采样器需要动态更新
- 聚合器需要接受参与 client 集合变化
- 新 client 需要同步当前 global model
- GGEUR 场景下新 client 还需要补交 local statistics
- global covariance/prototype 是否需要重算要有明确规则

适用场景：

- 长时间持续训练
- 用户上线/下线频繁

建议：

- 第二阶段再考虑
- 初始实现可以只允许在 round 边界加入
- 新 client 加入后先进入 `pending_clients`
- 下一轮开始前由 server 发送当前 global model 和必要全局统计

### 方案 C：在线立即加入

含义：

- 新 client 连接后立即参与当前 round 或当前训练阶段

不建议当前采用，原因：

- 会破坏同步 round 的参与集合
- GGEUR statistics 和 augmentation 阶段状态复杂
- 聚合权重、样本量、prototype/covariance 都可能需要重算
- 实验复现难度明显上升

当前结论：

- 不作为近期目标

### 推荐策略

多机验证阶段采用：

- 默认固定 client 集合
- join 窗口结束后不接受新 client 参与当前训练
- 新用户加入需求先记录为 future client admission
- 后续如需支持，优先实现“下一轮边界加入”，不要实现“立即加入”

## 六、客户端异步训练的处理方案

当前验证主要是同步联邦学习：server 等待本轮选中 client 的模型更新全部返回后再聚合。真实多机环境下，各 client 训练速度可能不同，需要明确如何处理慢 client 和异步返回。

### 问题来源

多机真实环境中，异步现象主要来自：

- 不同 GPU 性能不同
- 不同 client 数据量不同
- 网络带宽和延迟不同
- 某些 client 本地训练较慢
- 某些 client 临时中断或 OOM
- PromptFL / DomainNet 等任务计算开销不均衡

### 方案 A：同步等待全部 client

含义：

- 每一轮 server 等待所有选中 client 返回
- 全部返回后才聚合

优点：

- 逻辑最简单
- 与当前实现最一致
- 实验结果稳定、易复现
- 聚合权重明确

缺点：

- 最慢 client 决定单轮耗时
- 某个 client 卡死会拖住训练

现有缓解：

- `ggeur.distributed_stage_timeout`
- join timeout
- 崩溃场景验证

建议：

- 第一阶段继续采用该方案
- 通过 timeout 防止无限等待

### 方案 B：同步等待 quorum

含义：

- server 不要求所有 client 都返回
- 达到最小返回数量或比例后即可聚合
- 未返回 client 的更新丢弃，下一轮继续参与或降级处理

示例规则：

- `min_received_clients = ceil(sample_client_num * 0.75)`
- 超过 `round_timeout` 后，如果达到 quorum，则聚合
- 如果未达到 quorum，则本轮失败或重试

优点：

- 能缓解慢 client 问题
- 比完全异步更容易实现
- 仍保留 round 结构

缺点：

- 每轮参与集合变化会影响实验结果
- 需要记录实际参与 client
- GGEUR/FedProto 等统计或 prototype 路径要确认缺失 client 的处理

建议：

- 第二阶段优先考虑该方案
- 适合作为“半异步”过渡方案

需要实现：

- `round_timeout`
- `min_received_clients` 或 `min_received_ratio`
- 聚合时只使用已返回 client
- 日志记录 dropped/late client
- late update 默认丢弃

### 方案 C：完全异步联邦学习

含义：

- client 更新到达后 server 立即或小批量聚合
- 不再严格按同步 round 等待所有 client
- 需要处理 stale update

关键机制：

- update version：每个 client 更新携带基于哪个 global version 训练
- staleness：server 判断该 update 与当前 global version 的差距
- staleness weighting：旧更新降低权重或丢弃
- async aggregation：server 按到达顺序更新 global model

优点：

- 适合真实大规模在线 FL
- 不被慢 client 严重阻塞

缺点：

- 与当前框架差异大
- 实现复杂
- 结果复现和分析难度高
- GGEUR 的 statistics / augmentation / prototype 状态需要重新设计版本管理

当前结论：

- 不建议作为近期多机验证目标
- 可作为后续研究方向

### 推荐策略

多机验证阶段采用分层策略：

1. 第一阶段：同步等待全部 client，配合 timeout。
2. 第二阶段：引入 quorum 聚合，允许慢 client 被跳过。
3. 第三阶段：如确有需求，再设计完全异步 FL。

对当前项目最务实的路径是先把同步多机跑稳，再实现 quorum，而不是直接改成完全异步。

## 七、配置建议

建议新增或确认以下配置项。

### 新用户加入相关

```yaml
federate:
  allow_late_join: false
  late_join_policy: reject  # reject | next_round | async
  join_window_timeout: 300
```

第一阶段建议：

```yaml
federate:
  allow_late_join: false
  late_join_policy: reject
```

### 异步/慢 client 相关

```yaml
federate:
  aggregation_mode: sync_all  # sync_all | sync_quorum | async
  round_timeout: 1800
  min_received_clients: 0
  min_received_ratio: 1.0
  late_update_policy: discard  # discard | next_round_buffer | apply_with_staleness
```

第一阶段建议：

```yaml
federate:
  aggregation_mode: sync_all
  min_received_ratio: 1.0
  late_update_policy: discard
```

第二阶段可考虑：

```yaml
federate:
  aggregation_mode: sync_quorum
  round_timeout: 1800
  min_received_ratio: 0.75
  late_update_policy: discard
```

### GGEUR 阶段超时

当前已有：

```yaml
ggeur:
  distributed_stage_timeout: 1800
```

多机建议：

- OfficeHome 短链路：`600 ~ 1800`
- DomainNet 短链路：`1800 ~ 3600`
- 完整长实验：根据单轮实际耗时再设定

- `check_status.sh`：检查当前机器 PID、端口、日志
- `collect_logs.sh`：将多机日志拉回统一目录
- `run_connectivity_check.sh`：在启动训练前检查 server 端口可达

## 九、第一轮多机验证验收清单

### 环境验收

- server/client 机器 SSH 可达
- server 端口从 client 机器可连接
- client 端口无冲突
- Python 环境可运行
- 模型权重路径存在
- 数据路径存在

### 正常链路验收

- server 正常监听
- 4 个 client 全部 join
- 所有 client 获得 ID
- server 收齐 local statistics
- server 完成 global covariance/prototype 聚合
- client 完成 augmentation
- server 完成至少 1 轮模型聚合
- server/client 正常 finish

### 异常链路验收

- 少启动一个 client 时 server join timeout
- client 配错 server port 时有明确连接失败日志
- kill 一个 client 后 server stage timeout
- stop 脚本可清理残留进程
- 第二次启动不受第一次残留影响

### 结果验收

- 每台机器有独立日志
- 日志目录按时间戳归档
- server 日志可定位每个阶段
- client 日志可定位数据加载、训练、上传和 finish
- 运行结束后无残留训练进程

## 十、近期结论

近期多机验证应保持目标收敛：

1. 先验证跨主机通信和真实角色边界。
2. 第一阶段固定 client 集合，不支持训练中途新用户立即加入。
3. 第一阶段采用同步等待全部 client，依靠 timeout 处理慢 client 和崩溃 client。
4. 第二阶段再考虑 quorum 聚合和下一轮边界加入。
5. 完全异步 FL 和在线动态加入属于后续扩展，不应阻塞当前多机样板落地。
