# 周报（2026-05-21 至 2026-05-28）

## 一、本周工作概述

本周工作重点围绕 `FederatedScope / GGEUR` 的真实分布式训练推进展开。整体进展已经从“分布式基础设施可运行”推进到“真实数据集样板跑通、系统异常场景可验证、方法矩阵短链路通过”的阶段。

当前已经完成 `OfficeHome + GGEUR + FedAvg + CLIP ViT-B-16` 在真实 gRPC server/client 分布式进程下的完整链路验证，并进一步覆盖了端口冲突、client 延迟加入、client 缺失、client 崩溃、重复启动停止等系统场景。在此基础上，完成了 `OfficeHome` 与 `DomainNet` 下多种 GGEUR 相关方法的分布式短链路验证。

需要说明的是，目前验证主要是在单机多进程的真实 gRPC 分布式模式下完成，尚未覆盖两机或多机跨主机网络部署。

## 二、当前分布式整体进展

### 1. 分布式基础链路已经稳定

当前 server/client 基于 gRPC 的分布式启动、连接、ID 分配、消息收发、训练结束和资源释放流程已经具备可验证闭环。

已验证的系统能力包括：

- server 启动监听，client 正常 join
- client join 后由 server 分配真实 client ID
- client 延迟启动时仍可在 join timeout 内进入训练
- 缺少 client 时 server 可按预期超时退出
- 训练结束后 server/client 可释放 gRPC 资源并退出
- 受控脚本可管理 PID、清理进程并释放端口

### 2. GGEUR 分布式统计、增强和聚合链路已经跑通

本周完成了 `OfficeHome + GGEUR + FedAvg + CLIP ViT-B-16` 的真实分布式完整验证。该链路覆盖了：

- client 在 round 0 提取本地特征并上传 local statistics
- server 聚合 local mean / covariance / count
- server 生成并下发 global covariance、global prototypes 和 cross-client prototypes
- client 接收全局统计并执行 GGEUR feature augmentation
- client 完成本地训练并上传模型参数
- server 完成 FedAvg 聚合
- 训练结束后发送 finish 并完成收尾

关键验证日志已经出现：

- `Server: Broadcasted global covariances to 4 clients`
- `Server: Client 4 augmentation ready (4/4)`
- `Server: Round 1/2/3/4 aggregation complete`
- `Server: Training finished after 5 rounds`

同时确认 server 日志中不再出现 `No valid model parameters received`，说明分布式参数回传与聚合路径已经修复。

### 3. 单机可模拟的系统异常场景已基本覆盖

本周新增并验证了多类分布式异常场景，形成了 `system_short` 短链路回归入口。

已通过场景包括：

- `normal`：4 client 正常 join、统计、增强、训练、聚合、finish
- `delayed_client`：client 延迟启动后仍能进入训练
- `missing_client_timeout`：缺少 client 时 server 按预期超时退出
- `port_conflict`：server 端口被占用时明确失败
- `client_wrong_server_port`：client 配错 server 端口时出现明确连接失败日志
- `client_crash_after_join`：client join 后崩溃，server 在 statistics 阶段触发 watchdog timeout
- `client_crash_during_round`：client 在训练轮中崩溃，server 在 model update 阶段触发 timeout
- `repeat_start_stop`：server 连续启动/停止后无残留进程，端口可复用
- `system_short`：聚合上述短链路场景的系统回归入口

这部分工作使当前分布式系统在单机可模拟范围内具备较清晰的错误边界，不再只验证正常路径。

## 三、本周主要工作内容

### 1. 修复训练完成后 server 进程不退出问题

本周定位到分布式训练结束后 server 逻辑已完成但进程不退出的问题。根因是 gRPC 通信线程和 server 运行循环没有在 GGEUR 自定义 finish 路径中被完整关闭。

已完成修复：

- 为 `gRPCCommManager` 增加统一 `shutdown()` 接口
- server `terminate()` 改为幂等，避免重复发送 finish 或重复关闭通信
- GGEUR server `_finish()` 中显式关闭通信资源
- client 收到 finish 后主动关闭通信
- 对空 finish content 增加保护，避免被误当作模型参数更新

该修复保证了训练完成后 server/client 能正常释放 gRPC 资源，避免残留进程影响后续实验。

### 2. 跑通第一套真实 GGEUR 分布式样板任务

本周完成第一套真实样板任务的完整验证：

- 数据集：`OfficeHome`
- 方法：`GGEUR + FedAvg`
- 特征提取器：`CLIP ViT-B-16`
- 客户端数：`4`
- 模式：单机真实 gRPC server + 4 client 进程

本轮解决的关键问题包括：

- 分布式 gRPC 传输后 `(sample_size, model_para)` 从 tuple 变为 list，server 聚合逻辑需兼容 list
- 模型参数经过 base64/pickle 序列化后，server 聚合前需还原为 tensor
- 全局 covariance 下发时不能直接传递巨大嵌套 list，需要编码为紧凑 payload
- client 接收 `global_covariances` 后需要统一反序列化为 ndarray
- 高维 covariance 采样需要缓存分解结果，避免重复特征分解导致增强阶段耗时过高

最终 `normal` 场景通过，完整覆盖统计、增强、训练、聚合和收尾。

### 4. 新增 GGEUR 分布式阶段 watchdog

为避免 client 崩溃后 server 无限等待，本周新增 GGEUR 分布式阶段 watchdog。

新增配置：

- `ggeur.distributed_stage_timeout`

覆盖阶段：

- `statistics`
- `augmentation_ready`
- `round_N_model_updates`

验证结果：

- client join 后崩溃时，server 可在 `statistics` 阶段超时退出
- client 训练轮中崩溃时，server 可在 `round_1_model_updates` 阶段超时退出
- 超时后 server 会输出明确日志、通知已 join client finish，并关闭 gRPC server

### 5. 推进 OfficeHome 方法矩阵分布式验证

本周完成 OfficeHome 下多种 GGEUR 方法的真实分布式短链路验证。

覆盖方法：

- `FedProx`
- `FedOpt`
- `MOON`
- `FedProto`
- `PromptFL`

其中，`FedProx`、`FedOpt`、`MOON`、`FedProto` 主要验证无生成数据路径下的方法分支可用性；`PromptFL` 保留生成数据路径，验证 prompt learner、prompt loader、增强数据和参数上传聚合链路。

### 6. 推进 DomainNet 分布式方法矩阵验证

本周完成 DomainNet 下 GGEUR 分布式方法短链路验证。

覆盖方法：

- `FedAvg`
- `FedProx`
- `FedOpt`
- `MOON`
- `FedProto`
- `PromptFL`

本轮暴露并处理了 DomainNet 相比 OfficeHome 更明显的系统压力：

- DomainNet 类数更多，local statistics payload 超过 gRPC 消息上限
- 通过 `numpy + zlib + base64` 压缩，并用 float16 传输表示降低 payload 体积
- DomainNet PromptFL 并发 GPU 训练容易 OOM，短链路验证改用 CPU 路径
- PromptFL server-side 全量测试过重，支持 `eval.freq <= 0` 跳过验证阶段评估

最终 DomainNet 下上述方法均完成分布式短链路验证。

## 六、仍存在的问题与风险

当前还需要继续关注以下问题：

- 两机或多机真实跨主机网络验证尚未完成
- 多 client 分布到多台机器后的 IP、端口、防火墙和路径一致性还未联调
- 当前方法矩阵多数是短链路验证，还不是完整长实验结果
- DomainNet 完整训练和完整 test evaluation 的耗时、显存和 I/O 压力仍需单独评估
- PromptFL 在多 client 并发 GPU 训练下仍存在显存压力，需要进一步设计资源调度或分批策略
- 真实网络抖动、断链后的恢复策略尚未覆盖

## 七、下一步计划

下一阶段建议按以下顺序推进：

1. 做两机或多机跨主机 gRPC 联调，先验证 server/client 能跨机器完成 join 和 round 0。
2. 固化多机部署规范，包括 server IP、client 机器分配、端口、GPU 编号、数据路径、模型路径和日志路径。
3. 将 `OfficeHome + GGEUR + FedAvg` 从单机多进程扩展到真实多机样板。
4. 在多机样板通过后，再扩展到 `FedProx`、`FedOpt`、`MOON`、`FedProto`、`PromptFL`。
5. 选择少量代表性方法开始完整长实验，收集准确率、耗时、显存、通信 payload 和异常日志。
6. 将当前验证脚本整理成统一的一键巡检入口，并输出机器可读的结果汇总。
