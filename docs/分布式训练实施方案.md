# 分布式训练实施方案

本文档只关注 FederatedScope 的分布式基础设施实现，不绑定任何特定任务。

## 已落地内容

当前仓库已经补齐三类关键能力：

- 服务端 join 稳定性
  - 记录首个客户端接入时间。
  - 默认等待全部客户端接入的超时时间为 300 秒。
  - 超时后直接抛错并打印已接入 client 信息。
- 客户端乱序容错
  - 客户端在收到 `assign_client_id` 前，先缓存其他消息。
  - 分配到 ID 后再回放缓存消息，避免启动顺序和网络抖动导致异常。
- 受控启停脚本
  - 新增 `scripts/distributed_scripts/run_distributed_lr_managed.sh`
  - 新增 `scripts/distributed_scripts/stop_distributed.sh`
  - 用 PID 文件统一管理后台进程，便于 `Ctrl+C` 和兜底清理。

另外，日志初始化已经兼容 frozen config，避免分布式场景下输出目录创建时因为配置冻结而失败。

## 设计原则

分布式模式继续沿用 FederatedScope 原生 `distributed` + gRPC 架构，不再额外引入调度层。重点放在“让原有模式更稳”：

- 服务端必须先起。
- 客户端顺序启动，每个客户端之间保留 1 到 3 秒间隔。
- 所有客户端需要在服务端启动后的 300 秒内完成接入。
- 每个客户端监听端口必须唯一。
- 大模型场景必须显式调高 gRPC 消息大小上限。

## 推荐配置

最小分布式配置应包含：

```yaml
federate:
  mode: distributed
  client_num: 3

distribute:
  use: True
  role: server  # 或 client
  server_host: '0.0.0.0'
  server_port: 50051
  client_host: '0.0.0.0'
  client_port: 50052
  grpc_max_send_message_length: 314572800
  grpc_max_receive_message_length: 314572800
  grpc_enable_http_proxy: False
```

说明：

- `server_host/server_port` 是服务端监听地址。
- `client_host/client_port` 只在客户端配置中生效。
- `grpc_max_*` 建议默认按 300MB 起步，尤其是 ViT、CLIP、大型 MLP 或附带统计量时。

## 启动顺序

### 单机调试

使用：

```bash
bash scripts/distributed_scripts/run_distributed_lr_managed.sh
```

停止：

```bash
bash scripts/distributed_scripts/stop_distributed.sh
```

### 多机部署

1. 服务端机器先启动：

```bash
python federatedscope/main.py --cfg path/to/server.yaml
```

2. 客户端机器依次启动：

```bash
python federatedscope/main.py --cfg path/to/client_1.yaml
python federatedscope/main.py --cfg path/to/client_2.yaml
python federatedscope/main.py --cfg path/to/client_3.yaml
```

3. 如果任务较大，不建议手工逐台慢慢启动；应写统一脚本或用远程执行工具并发拉起。

## 现在这套实现解决了什么

### 1. 客户端启动早晚不一致

之前客户端如果在拿到 `assign_client_id` 前先收到了其他消息，容易状态异常。现在会先缓存，再在 ID 分配后回放。

### 2. 服务端无休止等待

之前服务端会一直卡在 join 阶段。现在超过 300 秒会明确报错，并输出已接入客户端信息，方便直接定位是数量不对还是网络不通。

### 3. 后台进程残留

之前直接 `&` 拉后台进程后，任务中断常常会遗留多个 Python 进程。现在 managed 脚本会记录 PID，并且做二次兜底清理。

## 部署建议

如果你继续推进真实多机分布式，建议按这个顺序走：

1. 先用当前 managed 脚本在单机验证分布式通信链路。
2. 再把目标任务配置拆成 `server.yaml + client_n.yaml`。
3. 把服务端和客户端的 `host/port` 改成真实机器地址。
4. 明确每个客户端本地数据、模型缓存和输出目录。
5. 最后再接入实际训练任务。

## 下一步最值得做的事

如果要继续完善，不建议再优先改 core 通信逻辑，而是做两件更直接的事：

- 为你的目标任务补一套专用的 `distributed_configs/`
- 为多机环境补一套 `start_server.sh / start_client.sh / stop.sh`

这样分布式基础设施就和具体任务解耦了，后面换数据集或模型时不用重新改一遍底层逻辑。

## 两机验证实施方案

下一步多机验证采用最小真实拓扑：

- 机器 A：只运行 server
- 机器 B：运行多个 client
- 两台机器通过真实网络 IP 和 gRPC 端口通信

该拓扑比“每个 client 一台机器”更容易控制变量，同时已经能验证跨主机通信、端口开放、角色边界和多 client 并发。

### 角色与端口规划

示例规划如下：

| 角色 | 机器 | 监听地址 | 端口 |
| --- | --- | --- | --- |
| server | 机器 A | `0.0.0.0` | `51151` |
| client 1 | 机器 B | `0.0.0.0` 或机器 B IP | `51152` |
| client 2 | 机器 B | `0.0.0.0` 或机器 B IP | `51153` |
| client 3 | 机器 B | `0.0.0.0` 或机器 B IP | `51154` |
| client 4 | 机器 B | `0.0.0.0` 或机器 B IP | `51155` |

如果机器 A 的真实 IP 是 `10.0.0.10`，机器 B 的真实 IP 是 `10.0.0.20`，则推荐：

server 配置：

```yaml
distribute:
  use: True
  role: 'server'
  server_host: '0.0.0.0'
  server_port: 51151
```

client 配置：

```yaml
distribute:
  use: True
  role: 'client'
  server_host: '10.0.0.10'
  server_port: 51151
  client_host: '0.0.0.0'
  client_port: 51152
```

说明：

- `server_host: 0.0.0.0` 表示 server 监听所有网卡。
- client 的 `server_host` 必须写机器 A 对机器 B 可达的真实 IP。
- client 的 `client_port` 必须在机器 B 上唯一。
- 如果框架或网络环境要求 server 能主动回连 client，则 `client_host` 应写机器 B 的真实可达 IP，而不是 `127.0.0.1`。

### 前置检查

两机验证前必须检查：

1. 两台机器代码版本一致。
2. 两台机器 Python/conda 环境兼容。
3. client 机器有训练数据和模型权重。
4. server 机器不需要访问 client 训练数据。
5. 机器 A 的 server 端口已放通。
6. 机器 B 的 client 端口已放通。
7. 两台机器系统时间大致一致，方便对齐日志。
8. 两台机器都可以写入自己的日志目录和输出目录。

建议命令：

```bash
# 机器 A：确认 server 端口未占用
ss -lntp | grep 51151 || true

# 机器 B：确认可以连到 server
nc -vz 10.0.0.10 51151
```

如果没有 `nc`，可以用 `telnet`、`curl` 或 Python socket 代替。

### 启动步骤

机器 A：

```bash
cd /root/autodl-tmp/FederatedScope
bash scripts/distributed_scripts/ggeur_officehome_vit_fedprox/start_server.sh
```

机器 B：

```bash
cd /root/autodl-tmp/FederatedScope
bash scripts/distributed_scripts/ggeur_officehome_vit_fedprox/start_client.sh 1
sleep 3
bash scripts/distributed_scripts/ggeur_officehome_vit_fedprox/start_client.sh 2
sleep 3
bash scripts/distributed_scripts/ggeur_officehome_vit_fedprox/start_client.sh 3
sleep 3
bash scripts/distributed_scripts/ggeur_officehome_vit_fedprox/start_client.sh 4
```

停止：

```bash
bash scripts/distributed_scripts/ggeur_officehome_vit_fedprox/stop.sh
```

注意：当前 `start_server.sh/start_client.sh` 默认使用样板 YAML 中的 `127.0.0.1`。进行两机验证前，必须先复制一套多机 YAML，或直接修改：

- server YAML 的 `distribute.server_host`
- client YAML 的 `distribute.server_host`
- client YAML 的 `distribute.client_host`
- 各角色 `outdir/expname`

### 验收标准

两机验证通过必须同时满足：

- server 日志显示全部 client join 成功。
- 每个 client 日志显示拿到不同的 `client_id`。
- GGEUR statistics 阶段完成。
- server 完成协方差聚合并下发全局协方差。
- client 完成增强并至少进入 1 个训练 round。
- finish 消息能触达 client。
- server/client 训练结束后正常退出。
- 两台机器均无残留训练进程。
- 日志目录中可以定位每个角色的完整日志。

### 异常场景验证顺序

两机正常路径通过后，再按以下顺序验证异常：

1. client 延迟启动，但仍在 join timeout 内加入。
2. 少启动一个 client，server 应在 timeout 后退出。
3. client 配错 `server_host`，client 应明确连接失败。
4. server 端口被占用，server 应启动失败。
5. 某个 client 中途退出，server 应有明确日志。
6. 重复运行脚本，确认旧 PID 和旧端口不会污染新实验。

### 不建议首次两机验证同时做的事

首次两机验证不要同时引入：

- 多台 client 机器
- 多 GPU 自动调度
- DomainNet 大数据集
- 多方法批量执行
- 复杂评估链路改造
- 自动远程调度系统

第一次两机验证只证明一件事：跨主机 gRPC 通信和 server/client 角色边界稳定。
