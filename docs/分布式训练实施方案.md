# 分布式训练实施方案

本文档只关注 FederatedScope 的分布式基础设施实现，不绑定任何特定任务。

## 已落地内容

当前仓库已经补齐三类关键能力：

- 服务端 join 稳定性
  - 记录首个客户端接入时间。
  - 默认等待全部客户端接入的超时时间为 300 秒。
  - 超时后直接抛错并打印已接入 client 信息。
- 客户端乱序容错
  - 客户端在收到 `assign_client_id` 前，先缓存其他消息。
  - 分配到 ID 后再回放缓存消息，避免启动顺序和网络抖动导致异常。
- 受控启停脚本
  - 新增 `scripts/distributed_scripts/run_distributed_lr_managed.sh`
  - 新增 `scripts/distributed_scripts/stop_distributed.sh`
  - 用 PID 文件统一管理后台进程，便于 `Ctrl+C` 和兜底清理。

另外，日志初始化已经兼容 frozen config，避免分布式场景下输出目录创建时因为配置冻结而失败。

## 设计原则

分布式模式继续沿用 FederatedScope 原生 `distributed` + gRPC 架构，不再额外引入调度层。重点放在“让原有模式更稳”：

- 服务端必须先起。
- 客户端顺序启动，每个客户端之间保留 1 到 3 秒间隔。
- 所有客户端需要在服务端启动后的 300 秒内完成接入。
- 每个客户端监听端口必须唯一。
- 大模型场景必须显式调高 gRPC 消息大小上限。

## 推荐配置

最小分布式配置应包含：

```yaml
federate:
  mode: distributed
  client_num: 3

distribute:
  use: True
  role: server  # 或 client
  server_host: '0.0.0.0'
  server_port: 50051
  client_host: '0.0.0.0'
  client_port: 50052
  grpc_max_send_message_length: 314572800
  grpc_max_receive_message_length: 314572800
  grpc_enable_http_proxy: False
```

说明：

- `server_host/server_port` 是服务端监听地址。
- `client_host/client_port` 只在客户端配置中生效。
- `grpc_max_*` 建议默认按 300MB 起步，尤其是 ViT、CLIP、大型 MLP 或附带统计量时。

## 启动顺序

### 单机调试

使用：

```bash
bash scripts/distributed_scripts/run_distributed_lr_managed.sh
```

停止：

```bash
bash scripts/distributed_scripts/stop_distributed.sh
```

### 多机部署

1. 服务端机器先启动：

```bash
python federatedscope/main.py --cfg path/to/server.yaml
```

2. 客户端机器依次启动：

```bash
python federatedscope/main.py --cfg path/to/client_1.yaml
python federatedscope/main.py --cfg path/to/client_2.yaml
python federatedscope/main.py --cfg path/to/client_3.yaml
```

3. 如果任务较大，不建议手工逐台慢慢启动；应写统一脚本或用远程执行工具并发拉起。

## 现在这套实现解决了什么

### 1. 客户端启动早晚不一致

之前客户端如果在拿到 `assign_client_id` 前先收到了其他消息，容易状态异常。现在会先缓存，再在 ID 分配后回放。

### 2. 服务端无休止等待

之前服务端会一直卡在 join 阶段。现在超过 300 秒会明确报错，并输出已接入客户端信息，方便直接定位是数量不对还是网络不通。

### 3. 后台进程残留

之前直接 `&` 拉后台进程后，任务中断常常会遗留多个 Python 进程。现在 managed 脚本会记录 PID，并且做二次兜底清理。

## 部署建议

如果你继续推进真实多机分布式，建议按这个顺序走：

1. 先用当前 managed 脚本在单机验证分布式通信链路。
2. 再把目标任务配置拆成 `server.yaml + client_n.yaml`。
3. 把服务端和客户端的 `host/port` 改成真实机器地址。
4. 明确每个客户端本地数据、模型缓存和输出目录。
5. 最后再接入实际训练任务。

## 下一步最值得做的事

如果要继续完善，不建议再优先改 core 通信逻辑，而是做两件更直接的事：

- 为你的目标任务补一套专用的 `distributed_configs/`
- 为多机环境补一套 `start_server.sh / start_client.sh / stop.sh`

这样分布式基础设施就和具体任务解耦了，后面换数据集或模型时不用重新改一遍底层逻辑。
