# 真实分布式联邦学习实施清单与计划

## 一、目标定义

当前项目的最终目标不是仅仅把 `distributed` 模式跑通，而是完成一套**真实可实施的分布式联邦学习体系**，满足以下条件：

1. 多台服务器真实联网运行
2. server 不持有客户端训练数据
3. 各客户端仅持有并访问自己的本地数据
4. 不同数据集可以部署
5. 不同模型可以部署
6. 不同联邦方法可以部署
7. 实验可以稳定启动、运行、停止、记录与复现

因此，当前工作不应只看“代码能不能跑”，而要看是否真正符合**真实联邦学习部署约束**。

## 二、当前尚未完成的内容清单

## 1. 严格数据隔离尚未完成

当前已有：

- client 端已支持按 `data_idx` 选择自己的数据子集
- GGEUR 数据加载器已支持按 client 切分数据

当前未完成：

- server 不能读取整份客户端训练数据
- server 不能从 `data.root` 主动加载所有 domain 的测试数据
- 真实部署时每个 client 应该使用预切分后的本地独立数据目录
- 当前还没有正式定义“预切分数据产物格式”

当前结论：

- 目前实现更接近“分布式运行的联邦模拟”
- 还不完全等价于“严格真实联邦学习部署”

## 2. 真实多机部署规范尚未完成

当前已有：

- 已有分布式脚本样板
- 已有第一套真实样板配置目录

当前未完成：

- server/client 所在机器清单
- 每台机器的固定 IP / SSH 别名
- 每台机器的 GPU 分配规则
- 统一端口分配规范
- 统一日志路径规范
- 统一模型缓存路径规范
- 统一数据路径规范
- 故障恢复规范

当前结论：

- 目前只有“能启动样板”的基础，还没有形成完整部署制度

## 3. 第一个真实样板任务尚未真正验证通过

当前已有：

- `OfficeHome + GGEUR + FedAvg` 的 distributed 样板目录

当前未完成：

- 在真实数据集上完成一次完整样板运行
- 验证 GGEUR 统计阶段
- 验证至少 1 个训练 round
- 验证真实退出流程
- 验证结果目录、日志、指标是否完整

当前结论：

- 配置已落地，但还没有形成“真实任务已跑通”的证据

## 4. server-side evaluation 不符合严格 FL 约束

当前问题：

- 当前 GGEUR server 会主动从 `data.root` 读取全域测试数据
- server 会自己提取特征并做集中评估

未完成项：

- 改为 client-side evaluation
- client 上报 metrics
- server 只做结果汇总

当前结论：

- 这部分必须改造，否则 server 仍然持有数据副本，违背真实 FL 目标

## 5. 真实数据预切分方案尚未落地

当前问题：

- 当前更多依赖“运行时切分”
- 真实部署更适合“预先切分 + 分发到各 client”

未完成项：

- 预切分产物格式定义
- 每个 client 的数据目录结构定义
- 数据切分脚本
- 数据分发规则
- 不同数据集的预切分统一规范

## 6. 多方法兼容性尚未验证

当前仍未系统验证以下方法在真实 distributed 部署中的兼容性：

- `FedAvg`
- `FedProx`
- `FedProto`
- `FedOpt`
- `MOON`
- `PromptFL`
- 其他已有 baseline / GGEUR 分支方法

风险原因：

- 不同方法可能有不同的 worker / trainer / message / state 管理逻辑

## 7. 多模型兼容性尚未验证

当前仍未系统验证以下模型分支：

- `CLIP / ViT`
- `CNN / ConvNeXt / ResNet`
- `timm / Mixer / GFNet`
- `MLP`

潜在问题：

- 权重依赖
- 显存压力
- 特征缓存逻辑
- 评估路径差异

## 8. 多数据集兼容性尚未验证

当前仍未系统验证以下数据集：

- `OfficeHome`
- `PACS`
- `DomainNet`

风险等级建议：

- `OfficeHome`：低，适合作为第一样板
- `PACS`：中，适合作为第二数据集
- `DomainNet`：高，建议最后推进

## 9. 启停、监控、清理体系尚不完整

当前已有：

- 基础 `start/stop` 脚本
- PID 文件思路

当前未完成：

- 多机启动脚本
- 单角色重启脚本
- 失败自动清理策略
- 日志归档规范
- 状态检查脚本
- 端口占用检查脚本
- 结果完整性检查脚本

## 10. 实验管理体系尚未完成

最终不是只跑一个实验，而是要跑很多数据集 / 模型 / 方法组合。

当前未完成：

- 配置命名规范
- 实验矩阵管理
- 结果汇总脚本
- 失败重试机制
- 对照实验模板
- 统一记录机制

## 三、实施路线总览

建议不要同时并行推进所有方向，而是按以下顺序推进：

1. 定义真实 FL 的硬约束
2. 改造数据与评估边界
3. 跑通第一个真实样板
4. 沉淀标准部署模板
5. 扩方法
6. 扩数据集
7. 做多机正式部署
8. 最后进入实验矩阵化

## 四、分阶段实施计划

## 阶段 1：明确真实 FL 基线约束

目标：

- 统一定义什么叫“实施完成”

建议作为硬标准的约束：

1. server 不持有客户端训练数据
2. server 不直接读取客户端测试数据
3. 每个 client 只访问自己的本地数据
4. 优先采用 client-side evaluation
5. 多机部署依赖预切分数据，而不是运行时切分

输出：

- 一份真实 FL 部署约束说明

## 阶段 2：重构数据与评估边界

目标：

- 把当前实现从“分布式运行的联邦模拟”改造成“真实式分布式联邦学习”

需要完成：

1. 明确 server 侧是否完全无数据
2. 修改 GGEUR server 的 test data 加载逻辑
3. 改成 client 本地评估 + server 汇总
4. 设计预切分数据格式
5. 设计每个 client 的数据目录结构

输出：

- 数据隔离设计文档
- 预切分格式规范
- server/client 数据职责说明

这是最重要的阶段。

## 阶段 3：跑通第一个真实样板任务

目标：

- 在真实数据上完成第一轮严格分布式样板验证

推荐样板：

- 数据集：`OfficeHome`
- 方法：`GGEUR + FedAvg`
- 客户端数：`4`
- 每个 domain 对应 `1` 个 client

验证内容：

1. 每个 client 只读自己的本地数据
2. server 不读训练数据
3. server 不直接加载测试数据
4. GGEUR statistics 阶段正常
5. 至少 1 个通信 round 正常
6. 正常退出和异常退出都可控

通过后，才能认定“真实样板可行”。

## 阶段 4：沉淀标准部署模板

目标：

- 把样板抽象成后续所有任务可复用的模板

需要沉淀：

- 通用 `server.yaml`
- 通用 `client.yaml`
- 多机 host/port 参数模板
- 数据路径模板
- 模型缓存模板
- 启停脚本模板
- 日志目录模板

输出：

- 标准 distributed 配置模板

## 阶段 5：先扩方法，再扩数据集

原因：

- 保持数据集不变时，更容易定位方法差异导致的问题

建议方法顺序：

1. `FedAvg`
2. `FedProx`
3. `FedProto`
4. `FedOpt`
5. `MOON`
6. `PromptFL`
7. `GGEUR` 其他分支能力

每种方法需要验证：

- trainer 是否兼容 distributed
- worker 是否兼容 distributed
- message / state 同步是否正常
- 评估逻辑是否符合真实 FL 边界

## 阶段 6：再扩数据集

建议数据集顺序：

1. `OfficeHome`
2. `PACS`
3. `DomainNet`

原因：

- `OfficeHome` 最适合作为第一样板
- `PACS` 次之
- `DomainNet` 最重，最容易暴露缓存、路径、I/O 和元数据问题

## 阶段 7：做多机正式部署

目标：

- 从单机分角色验证升级到多服务器联调

需要完成：

1. 明确机器映射表
2. 明确每台机器启动哪个角色
3. 分发预切分数据
4. 检查端口和网络连通性
5. 跑多机真实样板
6. 验证日志、结果和退出行为

通过标准：

- 多机 join 稳定
- 多机训练稳定
- 多机退出稳定
- 无残留进程

## 阶段 8：进入实验矩阵化

目标：

- 最终支持“各种数据集、模型、方法”的批量实验实施

需要完成：

- 每个数据集一个 distributed config 目录
- 每种方法一个配置文件
- 批量运行脚本
- 结果汇总脚本
- 对照实验表
- 失败重试机制

## 五、当前最优先要做的事

按当前项目进度，最优先的不是继续增加新样板，而是：

1. 明确并固化“server 不持有数据”的边界
2. 改造 GGEUR server 直接读 test 数据的逻辑
3. 再回头验证 `OfficeHome` 第一套真实样板

否则后面继续扩方法和扩数据集，会建立在不够真实的分布式前提上。

## 六、建议的下一步执行顺序

建议严格按如下顺序推进：

1. 先梳理 server / client 的数据职责边界
2. 再改评估链路
3. 再验证 `OfficeHome` 样板
4. 样板稳定后再扩方法
5. 方法稳定后再扩数据集
6. 最后做多机正式部署和实验矩阵

## 七、结论

当前项目已经完成了分布式基础设施和最小验证，但距离“真实分布式联邦学习完整实施”仍有明显差距。

最关键的差距不是“还缺多少 YAML”，而是：

- 数据隔离边界还未完全真实化
- 评估职责仍然部分放在 server
- 真实样板尚未严格验证
- 多方法、多模型、多数据集的推广路径尚未逐步打通

因此，后续工作必须从“真实约束”出发，而不是继续停留在“分布式样板能运行”的层面。

## 八、真实场景反应验证矩阵

在继续扩展 `FedProx`、`FedProto`、`FedOpt`、`MOON`、`PromptFL` 之前，需要先验证系统在真实分布式场景下对各种正常、异常和边界情况的反应。验证目标不是让所有场景都“成功训练”，而是要求：

- 正常场景可以稳定完成
- 可恢复异常可以明确恢复或重试
- 不可恢复异常可以快速失败并给出可定位日志
- 失败后不会污染下一次实验

### 8.1 启动与注册阶段

需要覆盖的情况：

- server 先启动，所有 client 正常加入
- client 先启动，server 后启动
- client 延迟启动，但仍在 join timeout 内加入
- 少一个或多个 client，server 应超时退出
- client 数量多于配置，server 应拒绝、忽略或明确报错
- client 重复启动，占用同一个 `data_idx`
- client 重复启动，占用同一个 `client_port`
- client 配置的 `server_host/server_port` 错误
- server 监听端口已被占用
- client 监听端口已被占用
- client 加入后立刻退出
- server 启动后没有任何 client 连接

预期要求：

- join timeout 必须生效
- 已加入 client ID 必须出现在日志中
- 端口占用和地址错误必须能从日志中定位
- 失败后 `stop.sh` 可以清理残留进程

### 8.2 配置一致性

需要覆盖的情况：

- server/client 的 `client_num` 不一致
- server/client 的 `total_round_num` 不一致
- server/client 的 `sample_client_num` 不一致
- server/client 的 `model.type` 不一致
- server/client 的 `model.num_classes` 不一致
- server/client 的 `data.type/root/splits` 不一致
- client 的 `data_idx` 超出范围
- 多个 client 使用同一个 `data_idx`
- `ggeur.embedding_dim` 与实际特征维度不一致
- 不同 client 使用不同 `feature_extractor`
- 不同 client 使用不同 CLIP/timm/CNN 权重
- FedProx/FedProto/FedOpt/MOON/PromptFL 等方法开关在 server/client 不一致

预期要求：

- 配置不一致应尽量在启动或统计阶段尽早失败
- 错误信息应指出具体 role、client、字段或维度
- 方法开关不一致不得进入静默错误训练

### 8.3 数据与文件系统

需要覆盖的情况：

- 数据集路径不存在
- 某个 client 对数据路径无权限
- 某个 domain 缺失
- 某个 class 没有样本
- 某个 client 本地训练集为空
- 图片损坏或无法读取
- feature cache 不存在，首次提取
- feature cache 存在且维度正确
- feature cache 存在但维度错误
- feature cache 文件损坏
- 输出目录无写权限
- 日志目录或 PID 目录无法创建
- 本地预训练权重不存在
- 本地预训练权重存在但文件损坏

预期要求：

- 数据路径、权重路径和写权限错误应在启动或特征提取阶段明确失败
- feature cache 维度错误应被丢弃或隔离，不得混入当前训练
- 损坏样本应有日志记录，必要时中止而不是静默跳过大量数据

### 8.4 GGEUR 统计阶段

需要覆盖的情况：

- 所有 client 正常上传 `local_statistics`
- 某个 client 不上传统计量
- 某个 client 上传空统计量
- 某个 client 只上传部分类别统计量
- client 上传的 `mean` 维度错误
- client 上传的 `cov` 维度错误
- client 上传的 `counts` 缺失或为 0
- 不同 client 的 embedding 维度不一致
- 协方差矩阵非正定
- 协方差矩阵含 `NaN/Inf`
- 类别 key 经通信后从 `int` 变成 `str`
- NumPy array 经通信后变成 list
- 高维协方差导致内存或时间压力过大

预期要求：

- server 聚合前必须校验 `mean/cov/counts`
- 维度错误必须定位到 `client_id` 和 `class_idx`
- 通信序列化导致的 key/type 变化应被规范化处理
- 大矩阵造成的性能问题应能通过日志判断阶段和耗时

### 8.5 GGEUR 增强阶段

需要覆盖的情况：

- 正常从全局协方差采样
- `num_generated_per_sample=0`
- `num_generated_per_prototype=0`
- `target_size_per_class=0`
- `use_cross_client_prototypes=False`
- 某个 class 没有本地样本但有其他 client prototype
- 某个 class 有协方差但没有 prototype
- prototype 维度错误
- covariance 维度错误
- Cholesky 分解失败后进入回退路径
- 增强后某 client 数据为空
- 增强数据量过大导致 OOM

预期要求：

- 增强关闭时应退化为原始特征训练
- 采样输入必须在 client 侧做类型和形状检查
- Cholesky 失败应有可控回退
- OOM 风险应能通过配置降低增强数量缓解

### 8.6 训练轮次阶段

需要覆盖的情况：

- 所有 client 正常训练并上传模型
- 某个 client 本轮训练失败
- 某个 client 上传空模型参数
- 某个 client 上传模型参数 shape 不一致
- 某个 client 训练很慢
- client 在某一轮中途退出
- server 在某一轮中途退出
- 网络短暂断开后恢复
- server 只收到部分 client 更新
- `sample_client_num < client_num` 时抽样训练
- FedProx proximal loss 正确启用
- FedProto prototype loss 正确启用
- FedOpt server optimizer 正确启用

预期要求：

- 模型参数 shape 不一致必须明确报错
- 慢 client 或丢失 client 不能导致无限等待
- 方法特有 loss/optimizer 应能从日志或配置中确认已启用

### 8.7 通信与序列化

需要覆盖的情况：

- 大消息发送：协方差矩阵、模型参数、prototype
- 消息内容为空
- 消息类型未知
- 消息顺序乱序
- 重复消息
- client 收到旧 round 的消息
- server 收到旧 round 的更新
- gRPC `Socket closed` warning
- gRPC message size 超限
- 通信序列化导致 dtype/key/type 变化
- server/client receive 阻塞

预期要求：

- 大消息必须通过 `grpc_max_send_message_length` 和 `grpc_max_receive_message_length` 约束
- 空消息和 finish 消息应被安全处理
- 旧 round 或重复消息不能破坏当前状态
- receive 阻塞必须有 timeout 或可中断路径

### 8.8 资源与性能

需要覆盖的情况：

- 单 GPU 正常运行
- 多 client 共享同一 GPU
- GPU 显存不足
- CPU 内存不足
- 磁盘空间不足
- 特征提取耗时过长
- 协方差聚合耗时过长
- 增强采样耗时过长
- 日志快速膨胀
- 进程退出后端口未释放
- 进程退出后 GPU 显存未释放
- 僵尸进程或残留 PID 文件

预期要求：

- 资源不足应明确失败或通过配置降级
- 关键阶段应有耗时日志
- 退出后端口、GPU、PID 文件应可清理

### 8.9 收尾与恢复

需要覆盖的情况：

- 训练完成后 server 正常发送 finish
- client 收到 finish 后正常退出
- server 释放 gRPC 资源并退出
- `stop.sh` 能清理所有进程
- 重复运行脚本不会被旧 PID 干扰
- 端口残留时能明确失败
- `Ctrl+C` 中断后能清理进程
- 失败后重新运行能复用或重建 cache
- 失败后不会污染下一次实验结果

预期要求：

- finish 路径必须幂等
- 清理脚本必须可重复执行
- 每次运行应有独立日志目录和结果目录

### 8.10 实验结果可信性

需要覆盖的情况：

- 每个 client 实际使用不同数据分片
- server 不持有 client 训练数据
- server 是否持有统一测试集有明确配置说明
- `seed` 固定后划分可复现
- FedAvg 与 FedProx 仅方法配置不同
- 日志记录配置、端口、PID、启动时间
- 训练完成后能找到最终指标
- 异常退出时能判断失败阶段
- 不同方法的 `outdir/expname` 不冲突
- 多次实验结果不会互相覆盖

预期要求：

- 每个实验必须能追溯配置、代码版本、日志目录和结果目录
- 对照实验之间只允许存在有意设计的差异

## 九、真实场景验证实施方案

### 9.1 验证分层

真实场景验证分为三层，不建议一次性测试所有异常。

第一层：正常路径。

- 目标：证明当前样板在标准条件下稳定
- 范围：server 先启动，所有 client 正常加入，完整跑完训练并退出
- 样板：`OfficeHome + GGEUR + FedAvg`
- 通过后再验证：`OfficeHome + GGEUR + FedProx`

第二层：可恢复异常。

- 目标：证明系统面对常见部署问题时不会无限卡住
- 范围：延迟 client、缺少 client、端口占用、旧 PID、cache 维度不一致
- 要求：必须明确超时、报错、清理或自动跳过坏 cache

第三层：必须失败且明确报错。

- 目标：证明错误配置不会静默进入错误训练
- 范围：维度不一致、模型参数 shape 不一致、数据路径错误、权重路径错误、方法开关不一致
- 要求：必须在启动、统计或聚合阶段尽早失败

### 9.2 建议测试顺序

建议按以下顺序执行：

1. 单机多进程正常路径：`FedAvg` 完整训练
2. 单机多进程正常路径：`FedProx` 至少 1 round
3. 单机异常：缺少 1 个 client，验证 join timeout
4. 单机异常：client 延迟启动，验证 join buffer
5. 单机异常：端口占用，验证失败日志
6. 单机异常：错误 `data_idx` 或重复 `data_idx`
7. 单机异常：损坏或旧维度 feature cache
8. 两机正常路径：一台 server，一台机器塞多个 client
9. 两机异常：server/client 地址错误
10. 两机异常：client 机器中途停止一个 client

### 9.3 每个场景的记录格式

每次验证都应记录：

- 日期时间
- git commit 或当前 diff 摘要
- 样板目录
- server 机器、client 机器
- server/client IP 和端口
- 启动命令
- 日志目录
- 预期结果
- 实际结果
- 是否通过
- 如果失败，失败阶段和下一步处理

建议统一回写到：

- `docs/分布式实施记录日志.md`

### 9.4 两机验证方案

目标形态：

- 机器 A：只运行 server
- 机器 B：运行多个 client
- 两台机器通过真实网络 IP 和 gRPC 端口通信

推荐角色分配：

| 角色 | 机器 | 进程 |
| --- | --- | --- |
| server | 机器 A | `server.yaml` |
| client 1 | 机器 B | `client_1.yaml` |
| client 2 | 机器 B | `client_2.yaml` |
| client 3 | 机器 B | `client_3.yaml` |
| client 4 | 机器 B | `client_4.yaml` |

网络配置原则：

- server 配置中的 `server_host` 建议使用 `0.0.0.0` 监听所有网卡
- client 配置中的 `server_host` 必须写机器 A 的真实内网 IP 或公网可达 IP
- client 配置中的 `client_host` 可以写机器 B 的真实 IP，若只需要本机监听也可先用 `0.0.0.0`
- 所有 `server_port/client_port` 必须在对应机器上未被占用
- 防火墙或安全组必须放通 server 端口和 client 端口

示例：

机器 A IP：

```text
10.0.0.10
```

机器 B IP：

```text
10.0.0.20
```

server 侧：

```yaml
distribute:
  use: True
  role: 'server'
  server_host: '0.0.0.0'
  server_port: 51151
```

client 侧：

```yaml
distribute:
  use: True
  role: 'client'
  server_host: '10.0.0.10'
  server_port: 51151
  client_host: '10.0.0.20'
  client_port: 51152
```

启动顺序：

1. 在机器 A 启动 server
2. 确认 server 日志进入等待 client join 状态
3. 在机器 B 依次启动 client 1 到 client 4
4. 观察 server 日志是否收到全部 client join
5. 观察 client 日志是否收到 `assign_client_id`
6. 至少跑通统计阶段和 1 个训练 round
7. 稳定后跑完整训练轮次
8. 验证所有进程正常退出

两机验收标准：

- 机器 A 的 server 不访问机器 B 的训练数据路径
- 机器 B 的多个 client 均能拿到不同 client ID
- server 能收到所有 client 的统计量和模型更新
- client 能收到全局协方差、模型参数和 finish
- 训练结束后两台机器均无残留训练进程
- 日志中可以明确定位每个角色、端口和运行结果

### 9.5 两机验证前置检查

执行两机验证前，必须确认：

- 两台机器代码版本一致
- 两台机器 Python/conda 环境一致或兼容
- 两台机器都能访问所需模型权重
- client 机器具备本地训练数据
- server 机器不需要 client 训练数据
- 两台机器系统时间大致一致，便于对齐日志
- `ping` 或等价网络连通性检查通过
- `nc -vz <server_ip> <server_port>` 或等价端口检查通过
- 防火墙、安全组、云平台网络策略已放通端口

### 9.6 暂缓项

以下事项不要在两机首次验证时同时引入：

- 多台 client 机器
- DomainNet 大规模数据集
- 多 GPU 调度
- 多方法批量运行
- server-side/client-side evaluation 大改造
- 自动化远程调度框架

两机首次验证的目标是证明跨主机通信和角色边界成立，不是证明实验矩阵已经可批量运行。
