# 6-25 周报：双机三级落地与参数读取 QPS 修正

## 一、本周目标

本周主要围绕 HeadOnly 方案在两台服务器上的实际落地展开，目标是将当前方案从最小通信验证推进到真实的双机三级结构验证。

当前部署对象为两台机器：

- 4090 机器：运行 root server 和 subserver 两个独立进程。
- 8G 机器：运行多个 client 独立进程。

系统结构保持为：

```text
client -> subserver -> root server
```

client 侧仍然采用读取已有 HeadOnly 特征缓存、训练 MLP、上传参数的方式；subserver 负责收集 client 参数、聚合后上传 root server；root server 等待所有 subserver 更新后完成全局聚合。

## 二、核心修改

### 1. QPS 统计口径调整

本周对 QPS 的定义进行了修正。此前 QPS 容易被理解为训练吞吐或简单的窗口响应数，本周明确改为只统计 client 与 subserver 之间的参数读取响应能力。

新的统计流程为：

1. client 读取特征缓存并训练 MLP。
2. client 训练完成后向 subserver 上传参数。
3. subserver 在上传等待窗口结束后聚合本轮收到的 client 参数。
4. subserver 将聚合结果上传 root server。
5. root server 完成本轮全局聚合后返回完成信号。
6. subserver 通知 client 可以读取新参数。
7. client 向 subserver 发起读参数请求。
8. subserver 只返回 ACK，不真实下发参数。
9. subserver 统计读参数 ACK 的响应 QPS。

当前 QPS 公式为：

```text
subserver_parameter_read_qps = responses / qps_denominator_response_window_sec
```

其中：

```text
qps_denominator_response_window_sec = 最后一个 ACK 发出时间 - 第一个读参数请求到达时间
```

同时保留 1 秒窗口内响应数作为辅助字段：

```text
responses_within_ready_window
responses_within_first_read_window
ready_window_qps
```

### 2. 缺缓存客户端跳过

当前 60 个 client 配置中，实际在本地找到并上传到 8G 机器的缓存文件为 55 个，编号为：

```text
client_000000.pt -> client_000054.pt
```

因此运行逻辑改为：

- 有缓存的 client 正常参与训练。
- 没有缓存的 client 暂时跳过，不参与本轮训练。
- subserver 的 `expected_clients` 按实际可用 client 数设置。

当前实际参与规模为：

```text
expected_clients = 55
```

缺缓存的 client 为：

```text
56, 57, 58, 59, 60
```

### 3. 训练和通信轮次

本周将全局训练/通信轮次设置为：

```text
total_rounds = 20
```

本地训练仍保持轻量配置，不以准确率为主要目标，当前重点是验证三级结构、参数上传/读取流程和 QPS 统计口径。

### 4. 上传等待窗口

subserver 等待 client 上传参数的窗口当前设置为：

```text
upload_timeout_sec = 10.0
```

该窗口表示 subserver 每轮等待 client 训练并上传参数的时间。窗口结束后，未完成上传的 client 会被视为本轮未参与，subserver 只聚合已经收到的参数。

## 三、已修复的问题

本周落地过程中修复了以下问题：

1. JSON 配置含 UTF-8 BOM 导致 4090 端读取失败。
2. PowerShell 中 `$PID` 是只读变量，导致 client 启动脚本报错。
3. `asyncio.Event()` 创建时机错误，导致 root/subserver 事件循环不一致。
4. 8G 机器缺少部分 client 缓存文件，导致启动前检查失败。
5. 一键远程启动中 4090 端 `python` 命令不存在的问题。
6. PowerShell 到远程 bash 的换行符和引号问题。
7. QPS 公式从“响应数”修正为“响应数 / 实际响应耗时”。
